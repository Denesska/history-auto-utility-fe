# Feature switches (per organization)

## Functionality

An organization can have individual features turned off (for example supplier management, the fleet cost dashboard or sale contracts). For members of that organization a disabled feature simply is not there: its menu entries, buttons and pages disappear, and fields that belong to it (such as the supplier picker when adding a document or a maintenance record) are not shown. Opening the address of a disabled page by hand sends you back to the Garage.

Turning a feature off never deletes data. Everything that was entered is kept, and it all comes back when the feature is switched on again. If an organization's feature is switched off while someone is using the app, the next action that needs it shows a short message ("This feature isn't enabled for your organization.") and returns them to the Garage.

Personal accounts are not affected: every feature is always available there.

## Implementation

- **Toggling a switch:** the app owner uses the admin screen's "Organizations & features" section (`features/admin`, `/main/admin`, app-owner only) — one card per organization with a toggle per feature, saved immediately via `PATCH /admin/organizations/:id/features`. There is no other UI for this; it used to mean editing `Organization.feature_flags` by hand in the database, which still works as a fallback but is no longer how it's normally done. See `features/admin/FEATURE.md`.
- **Source of truth:** the bootstrap response's `enabled_features: string[]` (hand-added to `BootstrapResponseDto` in `src/auto-gen/api/models/bootstrap-response-dto.ts`; `api-backend.yaml` is stale, do not regenerate). It is stored in `BootstrapState.enabledFeatures` (`string[] | null`, selector `BootstrapState.enabledFeatures`).
- **`FeatureService`** (`core/features/feature.service.ts`, root): `enabledFeatures` computed set and `isEnabled(key)`. Reads a signal, so it is reactive inside `computed()`/templates. **Rule: field missing (null: older backend, bootstrap not loaded yet, state reset) = ALL features enabled**, so nothing vanishes by accident. Keys live in `core/features/feature-keys.ts`: `FEATURE_KEYS` (`supplier`, `fleet_cost`, `sale_contract`, `documents`, `maintenance`, `car_notes`, `car_wishlist`, `journal`, `reports`) is the runtime array (mirrors the backend's `FEATURE_KEYS` in `common/features/feature-keys.ts`, and is what the admin screen reads to label known switches), and `FeatureKey` is its derived union type. The last six also back the car page's pluggable tabs/"add" actions — see `core/car-page/FEATURE.md`.
- **A reactive consumer must read `isEnabled()`/`enabledFeatures()` from inside a `computed()` (or otherwise keep re-reading it), not call it once and cache the result.** A plain method evaluated once at subscribe/construction time can capture a stale "not settled yet = all enabled" snapshot and never correct itself once bootstrap actually resolves — this was a real bug in `CarPageContributionsService`'s car-hub tab list (see `core/car-page/FEATURE.md`), fixed by wrapping the filter in `computed()` and exposing it as an `Observable` via `toObservable()`.
- **Loaded state:** `BootstrapState.featuresSettled` is set when a bootstrap attempt finishes (success, or failure = all enabled) and cleared by `reset()`. `FeatureService.loaded` exposes it; `whenLoaded$()` / `isEnabled$(key)` wait for it. `isEnabled()` stays synchronous for templates (all enabled until loaded). Anything that fires a feature's API request (the supplier fetches in documents form/detail, add-maintenance-panel, record detail) must use `isEnabled$()` so the request is never sent for a disabled feature.
- **Guard on hard load:** for routes with `feature`, `contextScopeChildGuard` waits for `whenLoaded$()` when not loaded yet, and starts the bootstrap itself (`BootstrapFacade.bootstrap()`, idempotent) because MainComponent only bootstraps after it renders, which is after the guard. Failure also settles, so it cannot hang.
- **Refresh:** switching organization goes through `select-organization.component.ts`, which calls `bootstrapFacade.reset()` (clears the switches to "all enabled") and `forceRefresh()` (reloads them for the new org). The 403 handler below also force-refreshes.
- **Routes/menu:** `ContextScopeData` (`features/main/context-scope.guard.ts`) has optional `feature?: FeatureKey`. `fitsContext(data, ctx, features?)` returns false when the feature is disabled; `contextScopeChildGuard` redirects to the garage. Tagged: `main.routes.ts` supplier and sale-contract routes, `organization.routes.ts` `costs/:organizationId` (fleet_cost; carries its own `scope` because the guard picks the deepest route declaring `scope`). Sidebar: `NavItem.feature` in `main.component.ts` (`saleContract`, `supplier`), filtered in `navItems`.
- **Hiding points:** settings (Account) screen Contracts and Suppliers entries (`showSaleContracts`, `showSuppliers`); organization page cost-dashboard button (`canViewCosts`); documents form supplier picker + supplier list fetch; add-maintenance-panel supplier picker + fetch; maintenance record detail and document detail supplier name (the supplier list is not fetched, so no name is shown).
- **403 `FEATURE_DISABLED`:** `features/auth/authErrorInterceptor.ts` shows a Transloco toast (`common.errors.featureDisabled`, en + ro), force-refreshes bootstrap and navigates to the garage; one toast at a time. The error is swallowed (`EMPTY`) so component error handlers do not add a generic failure toast. Navigation to the garage happens only if the current route itself has a `feature` (or no route data); a background fetch from another page does not navigate away.
- **Adding a new feature key:** add it to `FEATURE_KEYS` (and to the backend's `FEATURE_KEYS`/`UpdateOrganizationFeaturesDto`), put `feature: '<key>'` on its route data and sidebar `NavItem`, hide any settings entry / cross-feature UI with `FeatureService.isEnabled('<key>')`, add it to the hiding-point list above, and give it a label at `admin.organizations.features.<key>` (en + ro) so the admin screen shows a translated name instead of the raw key.
